# 0005. Home dinámico con SDUI, frente a Remote Config o Shorebird

**Estado:** aceptada

## Contexto
Cada segmento (joven, premium, emprendedor) debe ver un home distinto, y
el banco quiere cambiarlo sin publicar una versión nueva de la app.

## Decisión
Server-Driven UI acotado: `GET /experience/home` devuelve una lista de
componentes (`type` + `props`) armada por ms-customer según segmento, hora
y preferencias. La app tiene un `ComponentRegistry` con los tipos que sabe
dibujar.

- Un `type` desconocido o con props inválidas **se ignora** (compatibilidad
  hacia adelante).
- El layout se guarda en caché y se revalida con `ETag` (304).
- Sin backend ni caché se usa un layout de respaldo incluido en la app.
- Cada componente obtiene sus datos de su propio Bloc (cuentas, tipo de
  cambio), así que un servicio caído solo afecta su sección.

## Alternativas
- **Firebase Remote Config**: bueno para flags y textos, no para componer
  pantallas por cliente; además agrega un proveedor externo.
- **Shorebird (code push)**: cambia código, no datos; no resuelve la
  personalización por segmento y tiene implicaciones con las tiendas.
- **WebView**: rápido de cambiar, pero peor experiencia, accesibilidad y
  rendimiento.

## Consecuencias
- Solo se pueden componer componentes que la app ya conoce; un componente
  nuevo sí requiere publicar.
- El contrato (`type`, `props`) debe versionarse con cuidado; los tests de
  contrato verifican que los tres segmentos reales se pueden dibujar.
